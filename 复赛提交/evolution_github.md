These notes include historical development diagnoses, not guarantees about the injected project's current state. Detect existing baseline data and preserve original user edits/deletions/grants while applying missing new evolution seeds idempotently. Exercise both fresh databases and already populated databases lacking the new marker. A version-gated destructive seed alone is insufficient.

Inspect backend/src/routes/auth.js, orgs.js, repos.js and their callers. The baseline has frontend and backend already; preserve its layout. Its seedDatabase currently reruns destructive seedAcmeDocs operations: make original seeds versioned/idempotent before adding separate evolution seed versions. Within withTransaction use the supplied transaction methods, never the outer queued helpers (deadlock). New public GIVEN accounts use Evo-Password-987! unless specified otherwise. Provision all stated GIVEN records for the selected requirements without exposing a private test API, replacing existing user records or resetting any database. Keep original seed data and old public behavior.

For username registration permit a single hyphen or underscore between lowercase ASCII letters/digits; adjacent mixed separators, uppercase and leading/trailing separators are invalid. Match email case-insensitively only; usernames remain exact. Organization input normalizes uppercase to lowercase before cross-account/org uniqueness and insertion, display name only trims. Keep both invalid-field errors visible.

Search uses case-insensitive literal substrings in name OR persisted description, with the permission predicate governing both. Escape LIKE wildcard characters or use a literal substring operator. Keep Search as searchbox and exact result links.

Preserve the top Header global Search searchbox on repository and Manage access pages. Current public requirements distinguish the banner's global Search searchbox, the repository main area's local Search searchbox and the access picker's Search textbox. All can coexist; never hide, rename or remove the global control to satisfy a whole-page locator. The independent checks now use the appropriate role/scope and accept native options inside optgroup. If a developed workspace has `<Header hideSearch />` in ManageAccessPage, restore the global search there. Verify actual global submission and result navigation from both pages.

REQ-4-4 explicitly requires the created file VIEW to display saved content and its own Commits link to open the submitted commit message. An earlier local locator also matched the unsaved textarea and could reload the editor before save navigation. That check now excludes input/textarea and waits for the real file-view text; all refresh/history/atomicity assertions remain. Do not hide or clear the editor to satisfy the former ambiguous locator. If NewFilePage currently replaces its textarea with `Creating file…` while submitting, restore the original visible textarea and keep the existing submit guard. Keep the draft on failed saves. FileViewPage currently lacks the required Commits link; add the actual file-history navigation and show the persisted commit. Encode saved path segments when constructing a file-view address.

Issue description create/edit checks use the same non-editor text locator: after Save, actual displayed description must be present before reloading. Preserve draft fields on failures and retain backend confirmation; hiding or clearing an editor is not a substitute for saving its data.

BranchSelector choices must be role=option with accessible name equal to the branch name alone. Default badge must not enter this name. Filter live. Selected branch belongs in the URL and restores on reload; even the initial default branch must have an identifiable address. Escape/unmatched queries preserve it. Handle slash-containing names without rewriting default_branch or history. Inspect RepositoryPage and FileViewPage callers together.

Verify complete selected scenarios, existing login/signout/recovery and relevant permissions from home-page UI. Model finish is not acceptance. Independent public-source checks are read-only files in the Agent's evaluation directory; never modify them.

Preserve/repair the original REQ-1-1-3, REQ-1-2 and REQ-1-3 journeys, including cancel/confirm logout, only-current-session invalidation, protected-page refresh/back/direct entry, missing/incorrect current password, recovery and subsequent real sign-in. Read both frontend API DTO handling and backend responses; do not silence field validation.

AccountMenu regression: Your organizations must remain a genuine link (do not override with role=menuitem) when repairing Settings or Sign out. Home must expose exactly one visible Sign in and Sign up link; coordinate Header with HomePage. Recheck previous requirements after every batch, including a different local scope. The controller supplies actual current failures before asking for repairs.

Active sessions (REQ-1-4): migrate sessions compatibly with a separate safe display ID, device label and last-active timestamp. Existing session.id is an authentication secret and must never enter list DTO/DOM/URL. Use real independent browsers for the same account. Deny self-revocation here and cross-account revocation; revoked cookies must immediately fail loadCurrentAccount and remain inactive after two same-database restarts. Settings must keep Password and authentication and expose Active sessions. Preserve exact link roles in AccountMenu.

Audit (REQ-2-4): owner-only visible entry, direct page and API authorization. Persist semantic Actor/Action/Target/Timestamp rows and Member added/Repository created events; mutations plus their audit event must share one transaction. Filtering is read-only and reload-stable, preferably URL-backed. The existing add-member path is not transactional; use tx helpers while adding its event. Repository creation already has a transaction to extend. Give ordinary members no audit data. New seeds must run once without disturbing existing account credentials, sessions, org data or grants.

Local API conventions chosen for our independent checks (not dictated by the official YAML): GET /api/auth/sessions returns {sessions:[{id,device_label,last_active,is_current}]}; POST /api/auth/sessions/:safeId/revoke. GET /api/orgs/:name/audit-log returns {events:[{actor,action,target,timestamp,...}]}; frontend /orgs/:name/audit-log; the filter's clear option is All actions. Use these ordinary product APIs, not a test-only endpoint. Fields may be extended, but no authentication secret should be returned. These paths and field names are implementation choices; the public behavior remains authoritative.

Organization namespace follow-up from the public identifier/owner routing contract: normalization must reject collisions with existing account usernames as well as existing organizations. Current orgs.js checks only organizations; reject with Organization name already exists before writes, preserving the current account and creating no partial org.

Real shared-connection isolation regression: transactionQueue currently serializes only withTransaction, but plain run/get/all/exec can execute inside another request's open transaction. A real Node/SQLite check reproduced a successful external INSERT being rolled back by an unrelated failing transaction. Serialize all outer operations through the same queue; tx helpers use the raw connection. Audit inner callbacks for outer-helper calls and use tx methods to avoid deadlock. Keep the public-source test_evolution_github_database.py unchanged.

Concrete startup diagnosis from the supplied baseline: seed_db.js helpers seedRepoContent, seedPersonalRepositories, ensureBranch, ensureCommit, seedAcmeDocs, seedOrganizations, seedIssues and seedPulls destructure only run but call outer lexical get/all. Once database isolation is correct those reads deadlock inside seedDatabase's transaction. Thread the complete tx runner through these helper definitions and every call; keep version markers and seed writes in the same transaction. Do not disable the operation queue or move partially applied seeds outside that versioned transaction as a shortcut.

Actual Linux dependency diagnosis: repeated fresh register/login returned intermittent 401 despite correct credentials. A standalone test of the installed native bcrypt 6.0.0, without HTTP or SQLite, generated 400 hashes and compared each three times: nine iterations produced at least one false result; some comparisons of the identical password/hash changed true/false. The failure is reproduced in a public independent password compatibility check. Prefer the compatible pure JavaScript bcryptjs dependency for BOTH auth/validation.js and seed_db.js hashing, updating package metadata and lockfile through npm. Preserve all existing stored bcrypt hashes; never reset passwords, retry until success, reduce production rounds, or accept failed comparisons. Verify old independently generated bcrypt hashes, fresh register/login, wrong-password rejection and existing public accounts. Dependency documentation: https://github.com/dcodeIO/bcrypt.js . This is a measured local dependency issue, not a claim that all bcrypt installations fail.

Observed browser error on wrong-password submission: SignInPage's async handler reads e.currentTarget.password after awaiting login; React clears currentTarget after the synchronous callback, so this throws Cannot read properties of null and fails to clear the password. Capture the actual form element before awaiting, or use controlled field state. Preserve Invalid credentials, the entered identifier and no-session failure behavior. Verify real browser pageerror events and repeated correction attempts; do not remove the intended password clearing or suppress browser errors.

Archive/release/reaction increment (REQ-3-5, REQ-4-5, REQ-5-5): add compatible persisted fields/tables and independently versioned public GIVEN records, preserving prior data and bcrypt hashes. Cover all nine YAML scenarios through the existing repository UI. Archive and restore are Admin/org Owner actions, confirmed in named dialogs. An archived repository remains readable, with existing grants, files, branches, commits, issues and PRs intact; every mutation to it must be denied on the server, including issue metadata/comments/reactions, PR actions, files/branches/default branch/visibility and release publishing. Remove/disable corresponding UI actions. A fork writes a different new repository and can remain available on a readable archived source; do not blindly ban every POST containing its source path. Restore re-enables prior authorized actions. Recheck state inside serialized transactions for competing requests.

Releases are separate persistent metadata (tag, title, description, target branch) with repository-scoped unique tags. Public lists/details are readable without authentication; private reads follow repository visibility and real effective grants. Publish requires Write/Maintain/Admin/org Owner, validates the target, and atomically rejects duplicate tags with exactly Tag already exists, retaining original data. Releases is a repository navigation link, New release opens its form, and list tags are detail links. Persist all four fields and provide all three independent GIVEN repositories, including the duplicate-tag fixture before any test runs.

Reactions are permitted to any signed-in user who can read the issue, including a public reader without a direct repository grant. Add reaction opens a menu with +1 menuitem; the user's own highlighted control is Remove +1 reaction. Display type and numeric count, use a unique issue/user/type key and ownership-scoped delete, and never mutate issue content, labels, assignees, milestone or comments. Guests can see public counts but cannot act. Check issue read permission, authenticated identity and archived state separately. Existing issues.js wrongly treats direct repoRole as read visibility and queries nonexistent organization_members; use actual userCanAccessRepo semantics (including teams) and org_members. Do not weaken private repository permissions to repair public reads.

Local ordinary API conventions used by our independent checks (engineering choices, not extra official requirements): POST /api/repos/:owner/:name/archive and /restore; overview repository.archived boolean; GET/POST .../releases and GET .../releases/:tag with releases array/release object, fields tag/title/description/target_branch; POST .../issues/:number/reactions {type:'+1'}, DELETE .../issues/:number/reactions/+1; issue detail adds reactions [{type,count,reacted}]. # PR 公开需求与本地验收说明

来源为当前 GitHub YAML 的 REQ-6 完整父级合同与 12 项原子需求，共 25 个描述场景。检查代码逐场景映射，额外 API/SQLite 检查不计入公开场景数。每个 PR 界面场景用独立临时数据库和真实服务器；不会因先运行成功合并而污染随后被阻止合并的条件。这些都是本地独立检查，不能换算官方分数。

实现策略需要进入 Agent 的 evolution_github.md，应用代码仅由实际模型运行修改：

- Reuse existing pulls.js and repository routes; register actual list, compare/create and detail pages in App.tsx, plus Settings/Branches. Do not make a second repository implementation. Exact public link/button/heading roles and names matter; Commits, Files changed, Conversation, Checks are links. All pages work from home and on direct refresh. Only one active action of each name, except repeated changed-line Add comment buttons. Signed-in username remains visible; collect real pageerror events.
- Fix buildDetailPayload's `const isAuthor = isAuthor(...)` local-variable shadowing. Keep all existing payload fields. Distinguish changed files from unchanged files. Commits represent compare history relative to base, not unrelated baseline commits. Visibility checks use the existing permission predicate including public guest and team access; effective write/review/Admin checks must include inherited team/org roles where applicable.
- Additional concrete baseline defect: computeMergePermission selects `type` from organizations, but that table has no type column. Owner type is a discriminator constructed by getOwnerByName, not stored in that table. Every isOrgOwner call must apply only to an organization namespace; accounts.id and organizations.id are separate ID domains and may have the same numeric value. Owning an unrelated organization must never grant access to a personal repository with the same owner ID.
- All 25 public GIVEN states must exist independently before any scenario starts. Existing baseline seeds provide PR titles and roles in acme-demo/acme-docs, but inspect whether branches, base snapshots, approvals and checks are internally valid. The old seeded approvals use null commit IDs and old base_snapshot is '{}'; these do not establish the required mergeable state. Repair incomplete seed metadata through a new, atomic, idempotent migration with explicit eligibility checks, preserving user edits, existing authored content, deletions, status transitions and granted/revoked permissions. Do not rerun old seedAcmeDocs or erase files to fabricate a clean comparison. Do not overwrite an already valid user's decisions or changes on restart.
- The first new feature scope may have added a minimal PR list only. Complete Compare/Create/Draft/Ready/Overview/Diff/Review/Reviewers/Checks/Merge/Close/Reopen in this scope. Identical comparison disables create immediately when selecting both main branches. Whitespace title must be rejected with no partial PR. Pending review and published comments are different persisted states. Local API engineering choice is review-comments JSON {body,path,line,pending}; pending reflects only the requesting reviewer's pending work. Submit review publishes that user's pending comments. Invalid line/path anchors and self-review/non-reviewer actions are denied. Reviewer picker shows eligible non-author Write/Maintain/Admin users; removal only deletes the request, not reviews.
- A compare-branch commit updates PR current_commit_id and stales prior decisions/checks and marks existing line comments Outdated while preserving original commit/path/line. The original pulls.js omits outdated comments from the response: retain and render them. Current checks must be bound to the compared commit, not just PR ID/name; setting test success for an old commit cannot satisfy a later commit. Original comments schema needs a separate pending field. Do not merely rename all inline comments Pending review.
- Merge is a serialized transaction that rereads authenticated permission, current PR status, source/target heads, conflicts, current reviews/checks and exact-branch protection inside that transaction. Do not use outer queued database helpers inside withTransaction; pass tx helpers through readers or refactor the computation to accept a runner. Merged is terminal, concurrent requests can create at most one merge result, and ordinary errors must return JSON without crashing/hanging the server. A real SQLite trigger checks that failure while marking Merged rolls back new commits/files/PR changes; this is failure injection in a test-owned DB, not mocked app code.
- Implement actual three-way integration against the PR base snapshot; preserve target-only changes and reject conflicting edits. Original merge deletes all target files and replaces them with source files; that loses unrelated target changes. A new merge commit has both real parents, including any newer target head. Compatible local schema choice: commits.second_parent_id alongside existing parent_id. Record merger, timestamp and commit ID and expose it visibly. Only Create a merge commit is supported. Preserve normal branch/file creation and original commit history.
- PR comparison/detail commits must exclude unchanged base history. The old create-branch route copies files only and does not establish a source-head reference; the separate fork route copies commit rows. Inspect these distinct paths before changing them. Preserve historical rows and genuine branch-head/parent relationships so relative history is based on ancestry, not deduplication by message. A new source commit may legitimately have the same message as an old base commit; our real API check exercises that case. The current relative-history check already passes; preserve that behavior and do not delete old commits to make the display shorter.
- Protection rules are independent: only requested approval/check requirements apply. Unprotected targets still reject valid Request changes and conflicts, but require no extra approval or check. Draft, Closed, Merged, permission loss and archive state disable/reject merge. Required current approval must come from a non-author eligible reviewer. Close/reopen preserve branches, discussion/reviews and record activity; Read non-authors have no controls and direct requests fail.

对本轮生成代码的额外审查：NewReleasePage 当前始终渲染 Publish release 表单。即使列表隐藏 New release，访客或归档仓库直接打开 `/releases/new` 仍可能看到可操作提交按钮。接入下一次验收时补查直接页面的权限/归档限制；等待仓库与默认分支实际加载成功后才允许提交，不能用固定等待掩盖默认分支加载竞态。

Observed first-upgrade regression: the original supplied database has zero PR/review/protection/check rows; seedPulls existed as an unused definition. After enabling it, the old ensurePull updates a PR selected by fixed number. A real independent versionless-database migration check changed existing PR #1 to title 'User authored proposal', a user description and Closed status; startup silently restored 'Improve onboarding' and Open. Preserve existing authored PR IDs, numbers, title, description, status, branch/commit references and snapshots during first migration as well as normal restarts. Existing branch-protection policy must also survive. Do not call the old destructive seed helpers unconditionally, or increment seed versions to reset all fixtures. Provide missing public GIVEN records without overwriting a colliding existing record, and apply each new seed/migration and marker in one transaction. Read test_evolution_github_pull_storage.py for the real preservation check.

The account/organization numeric-ID collision check now covers PR review, inline-comment, check-setter and protection endpoints too. pulls.js canWriteRepo and canAdminRepo still queried isOrgOwner(owner.id, account.id) for a personal owner in the reviewed implementation. Fix every effective-permission path consistently; fixing merge alone leaves unauthorized review/admin actions. Keep Read/self-review denial and actual Write/Maintain/Admin/org Owner behavior.

Reproduced remaining lifecycle race after the merge transaction was fixed: two actual authorized HTTP requests, merge and close, both returned 200 (Merged and Closed) on the same Open PR. merge rereads state in its transaction, but close/reopen/ready read the PR outside their transaction and later unconditionally UPDATE the saved ID. This can overwrite the terminal Merged state. Read test_evolution_github_pull_concurrency.py: each competing merge/close pair must have one success and one 409, and the final state must match the winning action. Fix the shared transition boundary with transaction-local current PR, repository archive and effective permission checks, or an equivalent conditional update in the same transaction; rejected transitions must not append activity. Apply the same protection to ready, close and reopen, preserving successful ordinary flows and all data. Do not modify the independent tests or serialize client requests as a workaround.
